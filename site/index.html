LLM Training, In Reverse

Most training tutorials start from a gradient and build up, and you reach the part where the model talks back hours later. This course runs the tape backwards. We start from a finished chat model, undo its training one stage at a time back to a single weight update, and then rebuild the whole pipeline ourselves: a tokenizer, a model pretrained from scratch, and a chat model of our own.

The pipeline, read right to left

random weights→ pretraining 05, 11→ base model→ SFT 03→ preferences 04→ chat model

Every stage runs the same loop: predict the next token, measure how wrong you were, nudge every weight a little. Only the data and what gets graded change. Part 1 rewinds this pipeline on a real model. Part 2 opens up a single step of that loop. Part 3 builds the pipeline again from zero.

Lesson 01 · lessons/01_two_models.py

Two models, one body

A base model and its chat version: what is actually different?

SmolLM2-135M is a base model: it read trillions of tokens of web text, books and code, and learned to continue documents. SmolLM2-135M-Instruct is the same model after a few more rounds of training that turned it into an assistant. Same architecture, same 134.5 million parameters, same tokenizer. Only the numbers inside the weights differ.

That's worth checking rather than assuming. The lesson counts the parameters (134,515,008 in both), compares the shape of every tensor (all identical), and diffs the two config files: the only differences are the ids of the "beginning" and "end" tokens. Whatever post-training did, it did by changing the values of weights that were already there.

So the best way to see what that extra training did is to ask both models the same thing, two ways: as plain text, and wrapped in the chat template the instruct model was trained on. We use greedy decoding (always take the most likely token) so the differences come from the models, not from chance.

Four ways to ask one question

greedy decoding, 40 tokens

Empty means the model's first token was <|im_end|>: it ended its turn without writing anything.

Three things stand out. The base model answers plain questions like a document would. For France it happens to continue with an answer (plus an invented population). For the haiku it writes 10) Write an essay on…: to a base model, "Write a haiku about the sea." looks like item 9 on a homework sheet, so the likely next text is item 10. That isn't a bug. A base model was trained to answer one question, what text comes next on a typical web page?, and it answers it well.

The instruct model says nothing at all to a plain question. And inside the template the roles swap: the instruct model answers properly while the base model falls apart (a legless cave animal for "the capital of France"). Each model only works in the format it was trained on.

Why does the instruct model stay silent? Because it has only ever seen questions inside a template, and in every one of them a user's message was followed by <|im_end|>. To it, a bare question looks like a user message that just ended, so the most likely next token is "end of turn". It isn't refusing; it's waiting for the template.

Instruct, after a plain question

next-token probabilities

What the model actually reads

A "chat" is one string. Special tokens mark where each turn starts and ends. These tokens already exist in the base vocabulary, and the base model's config is identical apart from their ids.

The API's list of {"role", "content"} messages is turned into this string before the model sees anything. Even the system prompt, "You are a helpful AI assistant named SmolLM, trained by Hugging Face", is just 16 tokens of ordinary text that the template adds unless you supply your own. A model's sense of "who am I" is part of its prompt.

One more thing post-training has to teach: when to stop. Without it, every answer would run until the length limit and the app would have to guess where to cut.

Who knows when to stop?

tokens written before <|im_end|>, chat template, up to 120

The base model never stops: <|im_end|> almost never appeared in its training data. The instruct model stops on its own, except on the long list of sleep tips, where it runs out of room. Stopping is a learned habit, and lesson 03 shows how quickly it's learned.

Takeaways

  • Base and chat models share an architecture; post-training changes only weights.
  • The chat template is just text with special tokens. A chat model depends on it; the base model never learned it.
  • Each model behaves well only in its own format: the base model continues documents, the instruct model answers turns.
  • Post-training taught a format (the template) and a role (answer, then stop). Lesson 02 asks: what else did it change?

Lesson 02 · lessons/02_what_changed.py

What did post-training change?

We have both sets of weights. Subtract them: how big is the edit, where is it, and what did it cost?

Normally you only get the finished chat model. SmolLM2 publishes both ends of post-training, so we can see exactly what SFT and preference tuning did, summed into one number per weight. Call the difference Δ = Winstruct − Wbase.

For each weight matrix, compare the size of the change with the size of the matrix. The size here is just the square root of the sum of all squared numbers. Relative, because a change of 0.01 is huge for a weight of 0.001 and noise for a weight of 10.

How much each matrix changed

Rows: the nine kinds of weight in each of the 30 layers. Columns: layers. Darker means a bigger relative change. Hover for the value.

The edit is dense: only 7.3% of the weights moved by less than 0.001. A typical weight is about 0.107 and a typical change about 0.010, so almost every one of the 134.5 million numbers was nudged by roughly a tenth of its size. Post-training didn't find "the chat neurons" and rewrite them. It moved everything a little.

Two patterns stand out in the map. Layer 0 moved most: its value projection by 33%, the norm in front of it by 32%. That's where tokens are first read, and the chat template is full of tokens the base model barely used. The token embeddings moved by 11.7%, more than the average matrix, for the same reason. And queries and keys move more with depth, about 4–7% in the first layers and 11–12% in the last ones: late attention decides which earlier words to use for the next one, and a new role plausibly needs new choices there. (Plausibly: the map shows where, not why.)

Is a 8.6% change big? That depends on its direction. To check, add a random change of exactly the same size to the base model, and compare the result with the real one. Perplexity on a paragraph of encyclopedia text tells us whether the model still "knows" ordinary text (lower is better; lesson 06 explains the unit).

Same size, different direction

perplexity on encyclopedia text

The trained edit leaves the knowledge in place and adds a new behaviour. A random edit of the same size nearly doubles perplexity and doesn't chat; even a quarter of it costs as much as the whole trained edit. In 134.5 million dimensions almost every direction is harmful, and training found one of the few that help.

Dial in the edit

W = Wbase + α·Δ

"What is the capital of France?" in the chat template. α = 0 is the base model, α = 1 is instruct, beyond 1 overshoots. The small chart is perplexity on encyclopedia text along the way.

At α = 0.2, a fifth of the edit, the model already answers "The capital city of France is Paris". The rest of the way mostly changes the style. Watch the perplexity, too: it drops below the base model's between α = 0.1 and 0.75, then rises to 6.01 at α = 1. Part of the edit makes the model better at ordinary text, and the last stretch trades a little of that for chat style. Some forgetting does happen; it's just small. Overshooting to 1.25 hurts both.

So what exactly is different in the answers? Let the instruct model write a reply, then ask the base model, token by token: what rank would you have given this token? If post-training had rewritten the knowledge, the base model would disagree everywhere. If it changed the style, the disagreements should cluster.

The instruct model's reply, coloured by the base model's opinion

hover a token for its rank
rank 0 base agrees 1–2 3–9 ≥ 10 base would not have written this

They cluster. The tokens the base model would never have written are the opening word ("Absolutely" is rank 1,189 for the base model, "Here" 28), formatting (the "1" that starts a list, "**" for bold) and a few words that set the tone. Once the instruct model has written Here's my advice:↵↵1. **, the base model happily predicts much of the rest itself.

Even " Paris" is only rank 22 for the base model. That isn't missing knowledge: the base model said Paris to the plain question in lesson 01. Inside the chat template, it just has no idea a capital is being asked for.

Takeaways

  • Post-training is a small, dense edit (8.6% of the weights' size), aimed very precisely. A random edit of the same size only damages the model.
  • Knowledge survives: perplexity on ordinary text hardly moves. A fifth of the edit is enough to switch roles.
  • About half of the chat model's tokens are the base model's top choice anyway. The changed ones are mostly the first word, formatting and tone. This is the superficial alignment hypothesis (LIMA, URIAL, 2023).

Lesson 03 · lessons/03_sft.py

Do SFT yourself

How much data and time does it take to turn a base model into an assistant?

Supervised fine-tuning is ordinary next-token training with two changes. The data is conversations in the chat template, and only the assistant's tokens are graded. Everything else gets the label -100, which tells PyTorch's loss to skip it. That's all loss masking is. "Supervised" just means every example comes with the right answer: someone wrote what the assistant should say.

Our data: 2,260 short everyday conversations from the SmolLM2 team (greetings, budgeting, cooking, travel; no code, no maths, no poems), 119 more held out for testing. We start from the base model and train for about two minutes.

Which tokens get graded?

graded the model is trained to predict thisignored label = −100

Look at what is graded: the assistant's words and the <|im_end|> after them. That one token is how the model learns to stop. The header <|im_start|>assistant is not graded: at inference time we write it ourselves. And there's no system prompt; our models are trained without one, so we prompt them without one too.

The whole training loop fits on one screen. Take a batch of conversations, compute the loss on the graded tokens, call backward() to find which way each weight should move, and take a small step. The loss is cross-entropy: minus the log of the probability the model gave the real next token (100% → 0, 1% → 4.6), averaged over graded positions. Lessons 06–09 open up each of those lines.

for step in range(STEPS):
    x, y, att = pad_batch(next_batch(), device)
    logits = model(x, attention_mask=att).logits
    loss = F.cross_entropy(logits[:, :-1].flatten(0, 1),   # 1. how wrong are we?
                           y[:, 1:].flatten(), ignore_index=-100)
    loss.backward()                      # 2. which way should each weight move?
    opt.step(); opt.zero_grad()          # 3. move them a little

Training curve

Most of the drop happens in the first 50 steps; the next 150 only polish it. Learning a format is fast; it's the first thing a model picks up. And 200 steps × 8 is fewer conversations than the dataset holds: the model hasn't seen all of them even once.

Before and after

our own chat prompt, no system message

base model

after SFT

The first two prompts look like the training data; the last two don't. SFT taught format and role. It can't teach poetry from 2,000 everyday chats.

Before training, the base model writes the user's next message ("what is the best way to get rid of a bad smell in my house"): even inside the template it doesn't know which side it's on. After, it answers. France comes out right, a fact no training conversation taught; it was in the base model all along. The haiku fails, and the model asks you about the ocean instead.

And the book question gets "Hello! How can I help you today?": polite, right role, no book. That exact sentence is the assistant's first reply in 2,248 of the 2,260 training conversations. SFT copies the habits of its data, good and bad.

What masking did

test loss, before → after

All the training signal went to the assistant's side. The model learned to answer users, not to imitate them.

A warning about test sets

On this test set, our two-minute model beats SmolLM2-Instruct, which was trained on far more varied conversations and then preference-tuned. Ours specialised on everyday chit-chat; theirs didn't. A low loss on your own test set only tells you about data like your test set. The haiku is the proof.

The masking check is also a sanity check: if a bug had let user tokens into the loss, the user loss would have dropped too.

Takeaways

  • SFT is next-token prediction on conversations, with the loss masked to the assistant's tokens.
  • A few thousand examples and two minutes are enough to teach the format and the role, because the knowledge was already there. Most of it is learned in the first 50 steps.
  • SFT copies the style of its data. To teach a model to prefer one answer over another without writing the answers yourself, you need lesson 04.

Lesson 04 · lessons/04_dpo.py

Teach a preference, not an answer

With no correct answers at all, only "this one is better than that one", can you change how a model behaves? What does it cost?

SFT copies demonstrations: "here is the answer, write this". Often you don't have perfect answers, but you can easily say which of two answers is better. That's preference tuning. The production recipe used to be RLHF: train a reward model on human comparisons, then run reinforcement learning (PPO) against it. DPO (Direct Preference Optimization, 2023) gets the same effect with one loss function and no reward model.

Our toy preference: longer answers are better. Not because it's a good preference (it isn't), but because we can check it with len(). The algorithm never knows what a preference means; it only sees pairs labelled "this over that". A preference we can measure exactly is the best way to watch the algorithm itself.

We sample two answers per prompt from our own SFT model from lesson 03, call the longer one chosen and the shorter one rejected, and keep the pairs where both answers finished and the lengths differ by at least 8 tokens. No human labels, no new data. The model only ever chooses between things it already says.

Longer isn't better. The label only measures length, and the model will learn exactly that.

The loss, in five lines

Keep a frozen copy of the starting model: the reference. Score each answer by the sum of its tokens' log-probabilities (prompt masked, as in lesson 03), under the model being trained (π) and under the reference. The implicit reward of an answer is how much more likely the policy finds it than the reference does, and the loss pushes the chosen answer's reward above the rejected one's:

r(answer) = β · ( log π(answer) − log π_ref(answer) ) loss = −log σ( r(chosen) − r(rejected) )

Where does that come from? RLHF maximises "reward minus a penalty for drifting from the reference". The DPO paper showed that the best policy for that objective has a closed form, and turned it around: the reward is then β·log(π/π_ref), up to a constant that cancels when you compare two answers to the same prompt. So you can fit the policy directly on the pairs. The reference is the penalty.

β is the leash. With a small β, the loss stays high until the policy has moved far from the reference. With a large β, small moves are enough. At step 0 the policy equals the reference, both rewards are 0, and the loss is exactly log 2 ≈ 0.693.

We train twice on the same pairs: once with a sensible leash (β = 0.1), and once pulled hard (β = 0.01, four times the learning rate, two epochs), to see what over-optimising looks like.

What happened to the training pairs

log π − log πref, averaged over each batch (smoothed)

DPO only rewards the gap between chosen and rejected. Watch the signs: in both runs, both lines go down. The cheapest way to open the gap is to make short answers much less likely, not to make long answers more likely. Pulled hard, everything falls.

The cost

With the short leash, answers grow from about 33 to 59 tokens on prompts the model never trained on, and they still stop by themselves. The cost is a small rise in lesson 03's test loss: the model is now a little worse at the plain, short conversations it was trained on. That's the trade preference tuning always makes.

Pulled hard, the test loss triples. You'd expect the answers to be a mess. Read them:

The scoreboard

Our first draft of this lesson predicted the pulled-hard model would ramble, loop, or never stop. It doesn't. Its answers stop, read well, and aren't much longer than the sensible run's. Repetition barely moves. Every sample you'd read looks fine.

The damage is in the probabilities of everything the model doesn't say. Its test loss is now far worse than the base model's was before any SFT; its own chosen answers are much less likely than before training. It has moved into a narrow corner of its own while still winning on the training pairs. That's over-optimisation: it rarely shows in a handful of samples, and clearly shows in held-out measurements.

Real preference data has the same length trap: human raters tend to prefer longer answers. It's one reason chat models are so wordy, and one reason β and the reference model matter.

Takeaways

  • Preference tuning learns from pairs ("this over that") with no correct answer anywhere. DPO does it with one loss and a frozen reference model.
  • It learns exactly what the labels measure. We measured length and got length, not quality.
  • It has a cost on everything else. Pulled hard, it over-optimises silently: the samples look fine and the held-out loss triples. Always measure on held-out data.
  • That's the end of post-training. The facts, the grammar, the ability to write a sentence at all came from the base model. Lesson 05 rewinds into pretraining.

Lesson 05 · lessons/05_rewind_pretraining.py

Rewind pretraining

What does a model know at step 0, 128, 1,000, 143,000? In what order do skills appear, and does anything happen suddenly?

Everything left after post-training came from pretraining: next-token prediction on a huge pile of text, starting from random weights. We can't rewind SmolLM2's pretraining, because only its final weights were published. But EleutherAI's Pythia models were released with 154 checkpoints saved during training, and every Pythia model saw the same data in the same order. We take Pythia-70m (trained on 300B tokens of The Pile) and load it at 11 moments of its life.

On every checkpoint we run the same five probes: the loss on held-out WikiText (in nats per token: lower is better, and a uniform guess scores ln V ≈ 10.8); greedy completions of three prompts; the probability of the right next token for ten simple facts; copying, a passage shown twice, where a model that can look back gets the second copy almost free; and variety, how many different tokens it ever predicts as its top choice.

Scrub through training

greedy completions

P(right next token)

Drag the slider, or hover the chart. The x-axis is tokens seen on a log scale, because the interesting part happens early: Pythia's first checkpoints are spaced 1, 2, 4 … 512 steps apart, then every 1,000. Step 0 is drawn at the left edge.

Scrub from left to right and the skills arrive in order:

  • Step 0: random weights. Random tokens out; loss a little above ln V.
  • Step 128: it has learned which tokens are common, and nothing else. It writes "the the the". The random model predicted 990 different top tokens; this one only 40. Learning starts by collapsing onto the most common tokens.
  • 256–512: short phrases ("a little", "the first of"), in loops.
  • 512 → 1,000: copying switches on, and grammar follows.
  • After that: facts, slowly, roughly in order of how often they appear in text. "The United States of → America" is there by step 1,000. "Paris" never arrives: a 70M model is too small to store it, even after 300B tokens.

Two things about the facts are worth a second look. Knowledge flickers: "America" is at 79% at step 4,000, 5% at step 8,000, and back to 83% at 16,000. A checkpoint is a snapshot of a process that is still moving. And the France completion circles the answer without landing: "the capital of the capital" → "the capital of France, and the capital of France is…" → "the capital of the city of Paris" → back to "the capital of the country".

Copying from context

loss on a passage, 1st vs 2nd time

Variety

distinct top-1 predictions on 4,096 positions

Random noise is varied. Training first collapses onto " the", "," and "." and only slowly opens up again.

Copying doesn't fade in. It appears between two neighbouring checkpoints: on real text, the second copy of a passage costs 6.5 nats at step 512 and 2.0 at step 1,000. Nothing else on the page moves that much in one gap. This is the induction head phase change (Olsson et al., 2022): attention heads that look for "the last time this token appeared, and what came after it". Transformers, Inside Out lesson 07 finds them inside a finished model.

Most of the loss drop happens almost immediately. By step 1,000, 0.7% of training, the loss has fallen 85% of the way from where it started to where it ends. The other 99.3% of the compute buys the last nat, and that's where the knowledge lives.

A surprise: look at the dashed lines, copying random tokens (which can only be predicted by copying). It works best around steps 2,000–4,000 and then gets worse. By the end, even the first copy, which nobody can predict, costs more than twice the uniform guess: the model has become very sure about what comes next, and applies that confidence to noise too. Real-text copying stays fine. Don't assume more training improves every ability; measure the ones you care about.

Takeaways

  • Pretraining builds skills in a fixed order: token frequencies → phrases → copying from context → grammar → common facts → rarer facts. Fluency comes long before knowledge.
  • Most of the loss drop happens in the first 1% of training; knowledge lives in the long tail.
  • Some abilities switch on suddenly, some flicker, and some get worse.
  • Everything in Part 1 was measured with one number, the loss. What does 4.2 nats per token actually mean? Part 2 opens up the training step, starting there.

Lesson 06 · lessons/06_what_loss_means.py

What does the loss number mean?

What loss does a model get with no knowledge at all? With only counting? How do you compare models with different tokenizers, and how close are real models to perfect?

Every lesson so far printed a loss: 2.19 → 1.18 in lesson 03, 10.8 at Pythia's step 0 in lesson 05. Training is nothing more than pushing that number down, so before we look at how it gets pushed (lessons 07–09), it's worth knowing exactly what it measures.

loss = average over tokens of −log P(the real next token)

It's the model's average surprise. Probability 1 costs nothing; ½ costs 0.69 nats (1 bit); 1/1000 costs 6.9. Why a logarithm? Because the probabilities of a whole text multiply, P(token 1) · P(token 2 | token 1) · …, and the log turns that product into a sum. So a lower loss simply means the real text looked more likely to the model.

One loss, four ways of writing it

drag, or pick a model from this lesson

Perplexity = eloss: "as unsure as picking uniformly among this many tokens". A fresh model's perplexity is about its vocabulary size. Bits per character divides by how much text each token covers, and it's the only one of these you can compare across tokenizers.

The ladder

To see what a loss value is worth, score many models on the same text: TinyStories' validation set (children's stories, the data Part 3 pretrains on). Start from knowing nothing: equal probability for every one of its 97 characters, which costs log₂ 97 = 6.60 bits per character whatever the text. Every freshly initialised model starts here, at ln(vocab size) nats: that's Pythia's 10.8 in lesson 05.

Then just count. An n-gram model predicts the next character from counts of what followed the previous n−1 characters in 53.5 million characters of training stories. No neural network, no gradient: a lookup table. Then real neural models, all in one unit: bits per character.

Counting, on old text vs new

character n-grams

Counting goes a long way: the best lookup table, 6–7 characters of context, reaches 1.33 bits per character. Then the two lines split. On the text it was counted from, a longer context keeps helping (it's memorising). On new text it gets worse, 3.06 at n = 16: a 15-character context is usually a phrase the table has never seen, so it has nothing to say. That's overfitting in its purest form, and the reason every loss in this course is measured on held-out text. To do better, a model must generalise: treat "the dog ran" and "the cat ran" as similar without having counted both.

The token rows show why the unit matters. A uniform guess over SmolLM2's 49,152 tokens costs 10.8 nats per token, but each token covers about 4.1 characters, so per character it's 3.78 bits, already better than uniform over characters: the tokenizer's vocabulary of English chunks is itself knowledge. A token bigram (one previous token, about one word) gets 1.39, close to the best character table.

And the neural models: Pythia at step 1,000, the moment copying switched on in lesson 05, is only just past the best lookup table (1.28). By step 8,000 it's at 0.99, and the remaining 135,000 steps buy only 0.02 more on this text: simple English is learned early. SmolLM2, twice the size and trained on about 2T tokens, gets 0.66. Lesson 11 trains our own model on TinyStories and puts it on this ladder.

Where the loss is

SmolLM2's surprise on each token of one story · hover a token

Darker = more surprised. Each name and new idea is expensive the first time; when it comes back, it's nearly free.

An average hides a lot. The hardest tokens are choices the story could have made differently: the name "Roxy", the first verb, "icy", "a little bird named Billy". The 10% hardest tokens hold 32% of the story's loss. Then watch the second mentions: "oxy" costs 10 nats the first time and nothing after that; "hill" drops from 2.2 to 0.06. That's lesson 05's copying at work. What stays expensive is deciding when the name comes back.

Some of this surprise can never go away, because the story really could have gone another way (Billy could have been a dog). That irreducible part is the entropy of the text itself. Training pushes loss towards it, never below.

Takeaways

  • Loss = average −log P(next token). It starts at ln(vocab) for every model.
  • Counting gets to 1.33 bits/char, then starts memorising instead of generalising. Neural networks win by generalising.
  • Compare models in bits per character (or byte), never in loss per token across tokenizers.
  • Most of the loss sits in a few hard tokens; repeats are nearly free; some of it is irreducible. Next: how does each weight know which way to move to lower it?

Lesson 07 · lessons/07_gradients.py

What is a gradient, really?

What exactly is in p.grad? Can we compute it ourselves and check PyTorch? And what does one step along it actually do?

Every training loop so far had the line loss.backward(). It fills in p.grad for every weight: how much the loss would change if this one weight were nudged up a tiny bit. The sign says which way is downhill, the size says how steep it is here.

There's a way to measure that with no calculus at all, the finite difference: nudge the weight up and down by a tiny ε and see how much the loss moves. It needs two forward passes per weight, far too slow to train with, but it's a perfect referee. For a one-weight model, loss = (w·x − y)² with x = 3, y = 6, w = 1.5, calculus, the finite difference and autograd all say −9.0: increasing w lowers the loss.

The gradient every language model starts with

Our models end with logits → softmax → −log P(correct token). The gradient of that loss with respect to the logits has a famously simple form:

d loss / d logits = softmax(logits) − one_hot(correct token)

Read it as an instruction. The correct token: raise your score by 1 − p. Every other token: lower your score by its probability p. The tokens the model was most confidently wrong about get pushed down hardest.

softmax − one_hot

six logits from the lesson · click a token to make it the right answer

The pushes always add up to zero: the gradient only cares about which token wins, not about the overall level of the scores. And it explains lesson 03's loss masking: a position with label −100 is left out of the loss, so its row of softmax − one_hot is never computed and it sends no push at all.

Backprop is bookkeeping

Next, a tiny network (previous character → 16-number embedding → tanh layer → logits over 97 characters) with its backward pass written out by hand: one chain-rule step per line, from the loss back to the embedding table. Then a real tiny Llama (same architecture as SmolLM2, 2 layers), checked weight by weight against finite differences.

Hand-written backward vs autograd

float64, max |difference|

Differences of 1e-17 are float64's own rounding. Every line of the hand-written backward needed a value kept from the forward pass, which is why training needs so much more memory than inference (lesson 12).

Finite differences vs autograd

One weight from each of six tensors, nudged by ±1e-6. They agree to 7–9 significant digits, through attention, RoPE, SwiGLU and RMSNorm.

The first version of that check failed. The reason: Llama's RMSNorm quietly computes in float32 even inside a float64 model, and float32 rounding (≈1e-7) is larger than the change a 1e-6 nudge makes. Computing the norms in float64 for the check fixed it. Real training code is full of choices like this, about where to keep extra precision so that rounding doesn't eat the signal.

What does one step do?

The gradient says which way is downhill right here. Take one step of size η against it, w ← w − η·grad, on a 4-layer character model, and measure the loss again: on the batch the gradient came from, and on a different batch. The dashed line is what the gradient promises: a drop of η·‖grad‖² if the slope stayed the same all the way.

Loss after one step of size η

hover to read a step size

The promise is only local. Even at η = 0.01 the real drop is about three-quarters of it, and by η = 0.1 it's absurd (it predicts a loss of 1.4). The best single step is around η = 0.3; at η = 3 the loss doubles. One step that's 10× too big undoes everything.

The surprise is the second line: the step was computed on one batch, and the other batch improves just as much. At the start, the model knows nothing, so the first thing every gradient says is "spaces and e are common, Q is rare", and that's true of every batch. That shared structure is why training on one batch at a time works at all.

What does backward cost? On a 4.7M-parameter model on MPS, forward + backward took 4.0× a forward pass. In theory it's 3× (backward computes gradients for both the weights and the inputs, two matrix products for every one in the forward), which is where lesson 13's "6 × parameters × tokens" comes from. Small models measure more, because fixed costs like launching GPU kernels don't shrink with the model.

Takeaways

  • p.grad is the slope of the loss along one weight, computed exactly by backprop and checkable by finite differences.
  • For a language model it starts as softmax − one_hot and flows back through every layer by the chain rule.
  • Backward needs every activation from the forward pass and costs about twice the forward.
  • One step along −grad helps if small, hurts if big, and helps other batches too. Next: plain −grad isn't what anyone uses. What does Adam do?

Lesson 08 · lessons/08_optimizer.py

What does optimizer.step() do?

What does Adam do differently from plain gradient descent? Can we write it in a few lines and match PyTorch exactly? Why does it win, and what does it cost?

The gradient says which way is downhill for every weight. The optimizer decides how far to move each one. Four of them, each a few lines:

  • SGD: step along −grad. One learning rate for every weight.
  • Momentum: keep a running average of past gradients (a velocity) and step along that. Zig-zags cancel; consistent directions build up speed.
  • Adam: momentum, plus a running average of each weight's squared gradient. Divide by its square root, so each weight's step is measured in units of its own typical gradient.
  • AdamW: Adam, plus weight decay applied directly to the weights rather than mixed into the gradient.
m = β1·m + (1 − β1)·g             # running mean of gradients
v = β2·v + (1 − β2)·g²            # running mean of squared gradients
m̂, v̂ = m/(1 − β1ᵗ), v/(1 − β2ᵗ)   # undo the bias of starting at 0
w = w·(1 − lr·wd) − lr · m̂ / (√v̂ + ε)

Trained side by side with torch.optim on the same batches for 20 steps, ours match to the last bit of float32 (largest weight difference 1.2e-7). A recipe that says "AdamW, β = (0.9, 0.95), weight decay 0.1" is setting the knobs in those four lines.

A race on a narrow valley

Neural network loss surfaces are typically much steeper in some directions than others. The smallest version of that: a valley 250× steeper across than along, loss = 0.02x² + 5y², starting at (−9, 2). Each optimizer gets the fastest learning rate it can survive.

60 steps on a narrow valley

minimum at (0, 0)

SGD has one learning rate for both directions, and the steep one sets the limit: above 0.2 it overshoots across the valley and blows up. So it bounces across (y flips sign every step), settles that, and then crawls along the gentle direction. Momentum builds up speed along the valley, but overshoots across it too. Adam divides each direction by its own typical gradient, so both move at the same pace: its first step is exactly 0.5 in x and y.

The real race

Same thing on a 0.8M-parameter character model on TinyStories, 600 steps, same batches. For a fair race each optimizer gets its best learning rate from a sweep of four; with one shared learning rate you mostly measure which optimizer that rate happens to suit.

Not close. Adam ends at 1.16; momentum at 2.05, about where Adam was at step 100; SGD at 2.39. Switch to the SGD sweep: its two larger learning rates both sit at ~3.06 nats, the "letter frequencies" level from lesson 06. Too big a step doesn't always explode; it can just get stuck.

Why Adam wins

Look inside the trained model: how big is each weight's gradient, and how big is the step each optimizer would take with it?

Gradient vs step size

across all 816k weights

Common vs rare characters

mean |gradient| of their embedding rows

Size. SGD's learning rate is capped by its largest gradients, so the median weight moves about lr × median gradient per step. Adam's median step is 18× bigger, and the run stays stable. Adam's step is at most about lr, and typically less, because gradients that flip sign from step to step partly cancel in the running mean.

Spread. A rare character's embedding row appears in few batches, so its gradient is small: 19× smaller than a common character's here. With SGD it would learn 19× slower. Dividing by √v̂ evens that out, and it's why Adam's learning rate means roughly the same thing across very different models.

What it costs

Two extra numbers per weight (m and v). With fp32 weights and gradients, that's 16 bytes per parameter before any activations:

Training memory, before activations

fp32 weights + gradients + optimizer state

Running a model in bf16 needs 2 bytes per parameter. Training it with AdamW in fp32 needs 16, eight times as much, and activations come on top (lesson 12). Mixed precision and 8-bit optimizers shrink this.

Takeaways

  • Optimizers are short. Ours match torch.optim to float32 rounding.
  • SGD's single step size is capped by the steepest direction. Adam gives each weight its own scale, and on our model beats SGD by more than a nat in the same number of steps.
  • The price is two extra numbers per weight: 16 bytes per parameter for fp32 AdamW.
  • Adam still has one knob, the learning rate, and a 3× change in it can ruin a run. Next: how sensitive is that, and why does every recipe change it over time?

Lesson 09 · lessons/09_learning_rate.py

Why does the learning rate matter so much?

How sensitive is training to the learning rate? What does a failed run look like? Why warm up, why decay, and what does gradient clipping rescue?

Lesson 07: one step helps if it's small and hurts if it's big. Lesson 08: Adam's steps are a fraction of lr for every weight, so lr directly sets how far the whole model moves per step. Every real recipe also changes it during training: a warmup at the start, a decay at the end.

Same setup as lesson 08: the 0.8M-parameter character model, AdamW, 600 steps per run (about 12 seconds each). Every run starts from the same weights and sees the same batches, so the only difference between two runs is the thing we changed. One reference point from lesson 06: knowing only letter frequencies is worth 3.05 nats per character.

Final loss vs learning rate

7 constant rates, 3× apart · hover to pick one

Validation loss during training

A U-shape with a narrow bottom at 1e-3. Too cold, and the model learns steadily but slowly. Too hot, and the loss drops for a few dozen steps and then stops: the two hottest runs end at 2.58 and 2.99, around the letter-frequency level. They didn't blow up or spike (only the hottest run had any jump over 0.5 nats). Each step just keeps kicking the model out of anything finer than letter counts. A stuck run looks calm, and can be mistaken for a converged one; only the sweep tells you.

Near the bottom, a 3× change costs 0.09–0.18 nats. Two steps away it costs 0.45 on the cold side and 1.0 on the hot side: too hot is much worse than too cold.

Warmup: why start slow?

At step 0, Adam's running averages are empty and the random model's gradients are large and chaotic. A full-size step right away can push the model somewhere it never fully recovers from. Warmup ramps the learning rate up from almost 0 over the first steps (60 here). Test it at 3× the best rate, with three seeds:

Warmup, three seeds

At step 50 the two runs are about level. The damage of a hot start isn't a blow-up you can see early; it's a model that ends worse.

Decay: why end slow?

Late in training, the noise in each batch's gradient matters more than its direction: a full-size step mostly jumps around the minimum. Lowering the learning rate lets the model settle into it. Four schedules, same peak, same warmup: constant; cosine and linear decay to 10% of the peak; and WSD (warmup-stable-decay), constant until the last 20%, then a quick decay. Many recent models use WSD because you can stop or extend training at any point before the decay.

Until step 480, WSD is the constant run: same learning rate, same numbers, and it trails cosine. Then it decays, and in the last 100 steps it drops from 1.19 to 1.10, past everything else. The constant run, with exactly the same steps, ends at 1.17. The drop at the end comes from the decay itself, not from extra steps, so a run's loss before its decay is a pessimistic estimate of where it will finish.

Clipping: a seat belt

Sometimes one batch produces a huge gradient. Gradient clipping rescales the whole gradient whenever its norm exceeds a limit (1.0 is the usual choice), so no single step can be enormous. Test it at 10× the best learning rate, with warmup:

Both runs hit one giant gradient early: a norm of 36–43, against a median under 0.6. Clipped, the run ends at 1.38; unclipped, at 1.80. Clipping doesn't make a hot learning rate as good as the right one, but it makes it survivable. One likely reason a single spike hurts for so long: Adam's average of squared gradients (β2 = 0.999) remembers roughly the last 1,000 steps, so one giant gradient shrinks every later step. The lesson's Try tests that.

Takeaways

  • The learning rate has a narrow sweet spot. Too cold is slow; too hot gets stuck, quietly. Sweep it.
  • Warmup protects the first steps (better on 3 of 3 seeds); decay lets the model settle, and the final drop comes from the decay itself.
  • Clipping caps the damage of a bad batch. It's cheap, so nearly every recipe uses it (lessons 03 and 04 did).
